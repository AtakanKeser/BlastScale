# BlastScale load tests (k6)

Load tests for the BlastScale backend. The API is server-authoritative: a level only counts when
the server replays the submitted moves on its own copy of the board and gets the same score. A
virtual user therefore cannot just fire random requests; it has to *win* levels. This folder ships a
JavaScript port of the puzzle engine (`engine.js`) so every k6 VU generates the board from the
server's seed, solves it with the same greedy bot the backend uses for calibration, waits a
human-plausible time and then reports a result the server accepts.

## Files

| File | Purpose |
|------|---------|
| `engine.js` | Port of `SeededRandom`, `BoardState`, `BoardEngine.simulate` and `GreedySolver` from the Java engine. Runs in k6 and in Node. |
| `engine-vectors.json` | Copy of `docs/engine/engine-vectors.json`: 41 replay cases plus an RNG sequence generated by the Java engine. |
| `verify-engine.mjs` | Node script proving the port matches the Java engine bit for bit (`node verify-engine.mjs`). |
| `config.js` | Base URL, environment helpers, UUID generator, request parameter and `checkJson` helpers. |
| `flow.js` | The virtual player: login, config, daily reward, events, level start/complete/fail, wallet, leaderboard, plus all custom metrics. |
| `summary.js` | `handleSummary` implementation: compact console report and optional JSON file. |
| `smoke.js` | 1 VU, a few iterations, strict checks. Validates a deployment. |
| `scenario.js` | Realistic load with human think time, thresholds and configurable VUs / duration / ramp. |
| `stress.js` | Ramp to 2000 VUs with the shortest accepted think time to find the breaking point. No thresholds. |
| `results/` | JSON summaries land here when `RESULTS_DIR` is set (mounted at `/results` in docker compose). |
| `package.json` | Marks the folder as ES modules for Node (`npm run verify-engine`). Not needed by k6. |

## Running

### With docker compose (recommended)

The root `docker-compose.yml` defines a `k6` service (image `grafana/k6:1.1.0`) behind the
`loadtest` profile. It mounts this folder read-only at `/scripts`, `./load-test/results` at
`/results`, and presets `BASE_URL=http://nginx:8080`, so requests go through the same nginx load
balancer real clients use.

```bash
# bring up the platform first (add --scale api=3 to test horizontal scaling)
docker compose up --build -d

# validate the deployment: one player, three levels, every call must succeed
docker compose --profile loadtest run --rm --no-deps k6 run /scripts/smoke.js

# realistic load: 100 players for 2 minutes
docker compose --profile loadtest run --rm --no-deps k6 run -e VUS=100 -e DURATION=2m /scripts/scenario.js

# ramp 100 -> 500 -> 1000 players (about 11 minutes)
docker compose --profile loadtest run --rm --no-deps k6 run -e RAMP=1 /scripts/scenario.js

# find the breaking point (about 13 minutes, up to 2000 players) and keep the JSON summary
docker compose --profile loadtest run --rm --no-deps k6 run -e RESULTS_DIR=/results /scripts/stress.js
```

Every `-e NAME=value` after `run` is passed to k6 as `__ENV.NAME`. `RESULTS_DIR` is not preset:
add `-e RESULTS_DIR=/results` whenever you want the JSON summary written to `load-test/results/`.

### With a local k6 binary

```bash
k6 run -e BASE_URL=http://localhost:8080 smoke.js
k6 run -e BASE_URL=http://localhost:8080 -e VUS=50 -e DURATION=2m scenario.js
k6 run -e BASE_URL=http://localhost:8080 -e RESULTS_DIR=./results stress.js
```

`BASE_URL` defaults to `http://localhost:8080` (the nginx port of the compose stack). k6 1.x is
required (native ES modules, `http.expectedStatuses`, `handleSummary`); no jslib downloads are
needed, everything is local.

To only check that the scripts parse and evaluate without generating load:

```bash
docker run --rm -v "$PWD:/scripts:ro" grafana/k6:1.1.0 inspect /scripts/scenario.js
```

## The scripts

### `smoke.js`

One virtual player plays `ITERATIONS` (default 3) consecutive levels with the human think time
and logs every step (login, config, daily reward, board seed, solver result, reward, wallet,
leaderboard). Thresholds are strict, so the exit code tells you whether the deployment works:

| Threshold | Meaning |
|-----------|---------|
| `http_req_failed rate==0` | no unexpected HTTP status at all |
| `checks rate==1` | every response had the expected status and a JSON body |
| `errors rate==0` | no step ended in an unexpected outcome |
| `completions_rejected count==0` | the server accepted every replay |
| `levels_completed count>0` | at least one level was won and rewarded |

### `scenario.js`

The realistic loop. Each VU is one guest player that keeps its identity across iterations:

```
first iteration (app launch):  POST /auth/guest -> GET /config -> POST /economy/daily-reward -> GET /events
every iteration (one level):   GET /players/me -> POST /levels/{n}/start -> think time
                               -> greedySolve -> POST /levels/{n}/complete (or /fail when the
                               target was missed) -> GET /economy/wallet -> GET /leaderboards/weekly?limit=10
                               -> pause on the level map
```

| Variable | Default | Effect |
|----------|---------|--------|
| `VUS` | `50` | constant number of players |
| `DURATION` | `2m` | how long to keep them playing |
| `RAMP` | `0` | `1` = ramp 100 -> 500 -> 1000 players instead of constant VUs |
| `STAGES` | – | custom ramp, `duration:target` pairs, e.g. `30s:100,1m:500,2m:1000,30s:0` (implies `RAMP=1`) |
| `THINK_MS_PER_MOVE` | `200` | simulated thinking per TAP move; the server rejects anything below 150 |
| `THINK_BASE_MS` | `300` | fixed part of the play time per level |
| `LOBBY_PAUSE_MS` | `1000` | pause between levels (randomised between 50% and 150%) |
| `MIN_ITERATION_MS` | `1000` | pacing floor per iteration, keeps a player below the 600 requests/minute limit |
| `MAX_LEVEL` | `0` | cap the level a player plays (`0` = the player's real current level) |
| `PER_VU_CLIENT_IP` | `0` | send a distinct `X-Forwarded-For` per VU; only effective without nginx (see "Rate limits" below) |
| `LEADERBOARD_LIMIT` | `10` | `limit` query parameter of the weekly leaderboard |
| `VERBOSE` | `0` | log every step like the smoke test does |
| `P95_MS` | `500` | p95 latency threshold in milliseconds |
| `MAX_ERROR_RATE` | `0.01` | threshold for `http_req_failed` and `errors` |
| `REQUEST_TIMEOUT` | `30s` | per-request timeout |
| `RESULTS_DIR` | – | directory for the JSON summary |

Thresholds: `http_req_failed rate<1%`, `http_req_duration p(95)<500ms` (the completion call,
which runs the server-side replay, gets twice that), `errors rate<1%`, `checks rate>99%` and
`levels_completed count>0` (guards against a misconfigured think time silently producing zero
accepted levels).

### `stress.js`

Same flow, but with `THINK_MS_PER_MOVE=160` (just above the server minimum of 150) and a 250 ms
lobby pause, so every player produces as many requests as a human plausibly could. The default
ramp is 100 -> 500 -> 1000 -> 1500 -> 2000 VUs with holds, `MAX_VUS` scales it and `STAGES`
replaces it. There are no thresholds: the run never "fails", you read the point at which latency
and errors take off from the summary and from Grafana (`http://localhost:3000`).

## What a virtual player does

* **Identity.** Each VU logs in as a guest with device id `k6-<runId>-vu<N>-g<G>` (run id from
  `setup()`, VU number, generation). Device ids are unique per run, so a fresh run never inherits
  tired players from a previous one. The players are easy to recognise in the database and the
  admin panel.
* **Lives.** A player has 5 lives and regains one every 30 minutes. Every level start consumes a
  life, so after five levels the server answers `409 NO_LIVES_LEFT` and the VU simply becomes a new
  guest (`no_lives_left` and `players_created` count this). Expect roughly one new player per VU
  per five levels.
* **Progression.** The VU tracks `currentLevel` from the profile and `nextLevel` from each
  completion. A `403 LEVEL_LOCKED` (stale idea of the current level) triggers a profile refresh and
  one retry.
* **Solving.** `greedySolve(board, seed)` reproduces the board the server generated and pops the
  largest group until the target is reached or the moves run out (levels 1-5 are won practically
  always, later levels slightly less often). When the target is missed the VU reports
  `POST /levels/{n}/fail` with the moves it played, exactly like the client would.
* **Think time.** The server rejects completions faster than 150 ms per TAP
  (`blastscale.gameplay.min-millis-per-move`), so the VU sleeps
  `THINK_BASE_MS + moves * THINK_MS_PER_MOVE` between start and complete. Set
  `THINK_MS_PER_MOVE` below 150 on purpose to load-test the anti-cheat rejection path.
* **Idempotency.** Every completion carries a fresh `Idempotency-Key` UUID. When the request is
  lost or the proxy answers 502/503/504, the VU retries once with the *same* key, so the server
  either finishes the original or replays the stored response (`completions_replayed`,
  `retries`).
* **Rate limits.** Authenticated calls are limited to 600 per minute *per player*; the pacing
  floor keeps each VU far below that. Anonymous calls (`/auth/guest`) are limited per client IP
  with a much larger budget (3000 per minute by default) because real mobile traffic arrives
  from carrier NAT addresses shared by thousands of players — and because all VUs share the k6
  container's IP. nginx overwrites `X-Forwarded-For` with the real peer address, so a client
  cannot spread itself over fake IPs; `PER_VU_CLIENT_IP=1` sends a synthetic address per VU and
  is only useful when k6 talks to an API instance directly, bypassing nginx. A `429` makes the VU
  wait for the next one-minute window (`rate_limited` counts them).
* **Data.** The tests create real players, sessions and ledger entries. Run them against a
  disposable stack (`docker compose down -v` resets everything).

## Verifying the engine port

The server replays every move list, so the port in `engine.js` must be identical to the Java
engine: same RNG, same fill order, same gravity, same refill, same "regenerate while no pair
exists" rule, same greedy tie-breaking. `verify-engine.mjs` loads `engine-vectors.json` (41 cases
covering 8x8 and 6x7 boards, 4-6 colours, TAP/HAMMER/SHUFFLE moves, the extra-moves booster, an
invalid move, plus the raw RNG sequence) and asserts, for every case, the initial board, the replay
result (validity, score, moves, boosters, objective, stars) and the final board. TAP-only cases are
additionally re-solved with `greedySolve`, which must pick exactly the same cells in the same
order.

```bash
cd load-test
node verify-engine.mjs        # Node 20+ ; prints one line per case and exits 1 on any mismatch
```

Expected tail of the output:

```
PASS case 40: 8x8 colours=4 seed=777 extraMoves=false moves=1 -> valid=false score=0 stars=0

41 of 41 cases passed, 0 failure(s) (rng sequence ok, greedy solver cross-checked on 20 TAP-only cases).
```

When the Java engine changes, regenerate `docs/engine/engine-vectors.json` from the backend, copy
it over `load-test/engine-vectors.json` and run the script again before trusting any load test
result: a port that drifts from the server produces `SCORE_MISMATCH` / `INVALID_MOVE_SEQUENCE`
rejections, not load.

### Metrics

| Metric | Type | Meaning |
|--------|------|---------|
| `http_reqs`, `http_req_duration` | built-in | request count / rate and end-to-end latency (`p(95)` and `p(99)` are the numbers to watch) |
| `http_req_failed` | built-in | share of responses with an unexpected status; expected business rejections (see below) are excluded via `http.expectedStatuses`, so this is the real HTTP failure rate |
| `checks` | built-in | every response is checked for the expected status and a JSON body |
| `step_login`, `step_config`, `step_daily_reward`, `step_events`, `step_profile`, `step_level_start`, `step_level_complete`, `step_level_fail`, `step_wallet`, `step_leaderboard` | Trend | server round trip per endpoint; `step_level_complete` includes the server-side replay, `step_login` a database write |
| `levels_completed` | Counter | completions the server accepted and rewarded (`status: COMPLETED`) |
| `levels_failed` | Counter | levels where the greedy bot missed the target and `/fail` was reported (a business outcome, not a failure) |
| `completions_rejected` | Counter | completions the server refused; tagged with the error `code` |
| `completions_replayed` | Counter | completions answered from the idempotency store (`ALREADY_PROCESSED`) |
| `business_rejections` | Counter | all expected business errors, tagged with `code` |
| `no_lives_left`, `players_created` | Counter | player rotations caused by empty lives, and guests created (including the first one per VU) |
| `rate_limited` | Counter | `429 RATE_LIMITED` responses |
| `retries` | Counter | completions retried with the same idempotency key after a transport error |
| `errors` | Rate | share of steps that ended neither in success nor in an expected business rejection (the metric the thresholds use) |
| `solver_time`, `level_moves`, `think_time` | Trend | client-side solver cost, moves per level and the simulated play time |

Per-endpoint percentiles of the built-in metrics are available through the `name` tag, e.g.
`http_req_duration{name:POST /api/v1/levels/{level}/complete}`.

### Expected business rejections versus failures

The API answers gameplay rules with 4xx codes. The scripts know which of them are part of normal
play; those never count towards `http_req_failed` or `errors` and show up in `business_rejections`
(with the code as tag) instead:

| Code | Status | Why it happens | Script reaction |
|------|--------|----------------|-----------------|
| `NO_LIVES_LEFT` | 409 | the player spent its 5 lives; the next life comes in `details.nextLifeInSeconds` | log in as a new guest and continue |
| `LEVEL_LOCKED` | 403 | the requested level is above the player's current level | refresh the profile, retry once |
| `DAILY_REWARD_ALREADY_CLAIMED` | 409 | second claim on the same UTC day | ignore |
| `SUSPICIOUS_DURATION` | 422 | the completion arrived faster than 150 ms per move | counted in `completions_rejected`; with the default think time this should be zero, so if it appears check `THINK_MS_PER_MOVE` and the clocks of the API replicas |

Everything else is a failure worth investigating:

* `SCORE_MISMATCH`, `INVALID_MOVE_SEQUENCE`, `OBJECTIVE_NOT_REACHED`, `TOO_MANY_MOVES`,
  `SCORE_OUT_OF_RANGE` (422): the engine port and the server disagree. Run
  `node verify-engine.mjs`, and check whether the level definitions or the engine changed.
* `RATE_LIMITED` (429): the load profile pushed a player (or, with `PER_VU_CLIENT_IP=0`, the
  shared IP) over 600 requests per minute. Increase `MIN_ITERATION_MS` or the think time.
* `SESSION_NOT_FOUND`, `SESSION_NOT_ACTIVE`, `SESSION_EXPIRED`: the session was closed by
  something else; unexpected in these flows.
* `LEADERBOARD_UNAVAILABLE` (503): Redis is down, the leaderboard degrades on purpose.
* 5xx and status 0 (connection refused, timeouts): the server or the load balancer gave up. The
  stress test exists to find the VU count where these start.

### Exit codes and thresholds

k6 exits with `0` when every threshold passed and `99` when at least one failed, so
`smoke.js` doubles as a deployment gate in scripts and CI. `stress.js` has no thresholds and
always exits `0` unless the run itself aborts (the `setup()` phase aborts early when the readiness
probe `GET /actuator/health/readiness` cannot be reached).

### JSON summaries

`RESULTS_DIR` makes every script write `summary-<script>-<timestamp>.json` with the full k6
summary object (`metrics.<name>.values` holds the counts, rates and percentiles, including the
thresholds and their pass/fail flags). Example:

```bash
jq '.metrics | {rps: .http_reqs.values.rate, p95: .http_req_duration.values["p(95)"],
   failed: .http_req_failed.values.rate, completed: .levels_completed.values.count}' \
   results/summary-scenario-20260904T183000Z.json
```

The server side of the same run is visible in Grafana (`http://localhost:3000`, admin/admin) and
Prometheus (`http://localhost:9090`): request latency per endpoint, JVM and database pool metrics,
and the gameplay counters, e.g. completions rejected per validator
(`blastscale_completion_rejected_total{validator="duration"}`).
